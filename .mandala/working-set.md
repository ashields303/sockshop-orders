### SOCK-4: Accept, validate and persist shippingMethod; apply express fee; pass to shipping
Problem: NewOrderResource carries only customer/address/card/items, and OrdersController.newOrder (POST /orders, OrdersController.java:50) adds a fixed 4.99 shipping cost and posts a Shipment that holds only the customer ID (OrdersController.java:101). Approach: (1) Add an optional `shippingMethod` field to NewOrderResource, limited to 'standard' | 'express' (an enum or a validated string). A missing value defaults to 'standard' so existing callers keep working. An unknown value is rejected with HTTP 406, which matches the existing missing-field handling. (2) Compute the order total as the items total plus shipping. Standard keeps today's 4.99. Express adds a flat fee, and how it combines with 4.99 is still open (see open_questions). Put the fee amounts in configuration, for example on OrdersConfigurationProperties or a new property, not hardcoded in the controller. Make sure the payment amount sent to POST /paymentAuth reflects the new total. (3) Add shippingMethod to the orders-side Shipment entity posted to http://shipping{domain}/shipping. (4) Persist shippingMethod on CustomerOrder so it is returned by GET /orders/{id} and /orders/search/customerId. Out of scope: per-region pricing and carrier integration.
Acceptance criteria:
- Given a valid NewOrderResource with shippingMethod "express", when it is POSTed to /orders and payment is authorized, then the response is 201, the saved CustomerOrder has shippingMethod "express", and its total equals the items total plus the configured express shipping charge
- Given a valid NewOrderResource with no shippingMethod, when it is POSTed to /orders, then the order is created with shippingMethod "standard" and the total equals the items total plus 4.99, so behavior is unchanged
- Given a NewOrderResource with shippingMethod "overnight", when it is POSTed to /orders, then the service responds 406, and no payment, shipping, or MongoDB save call is made
- Given an express order, when OrdersController calls the payment service, then the PaymentRequest amount equals the express-inclusive total
- Given an order with shippingMethod "express", when OrdersController posts the Shipment to the shipping service, then the Shipment JSON body contains "shippingMethod": "express" as well as the customer ID
- Given a saved express order, when a client calls GET /orders/{id}, then the response body includes "shippingMethod": "express"
Test notes:
- (unit) JUnit: cover total calculation for standard and express, defaulting when the field is absent, and rejection of unknown values. Update UnitPojo.java: if a new ShippingMethod enum or class is added to the entities package, change the expected entity count (currently 8) to match.
- (integration) IT*.java under maven-failsafe (`mvn verify`) with embedded MongoDB (flapdoodle): mock the payment and shipping endpoints. Assert that the outbound Shipment body includes shippingMethod, that the payment amount is correct, and that the persisted order contains the field.
- (manual) POST /orders with curl, once with express and once without the field. Inspect GET /orders/{id} and the request the shipping service received.
